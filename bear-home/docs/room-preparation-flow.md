# 装修准备：用户意图与动线

用户的两种起点：
- “卫生间需要准备什么？”：选房间 → 参考准备项 → 查看选配参数、施工提问与笔记 → 添加候选 → 对比 → 选定 → 已买。
- “看到一个商品，先收下来”：随手记/商品链接 → AI整理或直接保存 → 对应准备项；尚未识别的内容进入房间的待归类区域，之后选择准备项。

## 信息层级

首页只展示房间、准备项概览与选定进度。房间内展示准备项及状态，而非全部商品。进入准备项后展示候选、报价、关键参数提示与相关笔记。具体参数在候选详情编辑，比较为主动操作。

房间：承载施工、布局等整体参考。
准备项：代表需要准备的物品，可无候选，可暂不需要。
候选：具体商品或门店方案，保存名称、价格及原单位、原文、链接、参数、优缺点和状态。
笔记：独立内容，可关联房间或准备项；不复制笔记正文。

## 首版边界

保留现有真实AI文字整理服务，不宣称自动读取链接。选购数据与关联关系保存在当前设备；笔记从服务器读取。卫生间候选A/B及旧记录是标明来源的演示数据，中央空调是用户给出的真实候选，未核实数据保持空白。房间参考项和施工提问不替代现场选型及产品安装说明。

## 已验证

房间→准备项→同类候选对比；单项选定互斥；参数补充；链接保存及候选移除；真实笔记关联与刷新保留。390px与320px屏幕无页面横向溢出，参数保存区可见。归类匹配优先精确品类与更长名称，避免床垫误归床。类型检查、归类回归测试与小程序构建通过。

## 待确认事项：已确认的设计，尚未实现（2026-10-14）

将准备项侧的静态“选配时看什么”收进参数对比与待确认事项。待确认事项记录真实未解决的问题，允许用户自由添加，不局限于预置字段。

- 支持房间、准备项、候选三个关联范围。例如卫生间插座位置、马桶坑距、某款马桶报价是否含安装。
- 添加：点击“＋ 待确认”，写一句话；从当前页面自动带入关联范围。允许编辑、删除。
- 解决：勾选完成，可选补充结论、依据或关联笔记。完成和结论分开，不能将勾选完成当作参数已核实的证据。
- 展示：默认只显示未解决的事项，已完成项折叠并可重新打开；在候选页可见对应准备项及房间的相关问题，并标出所属范围，避免重复创建。
- AI 建议：与手动事项分开，用户逐条或批量接受后加入；不得把所有空参数直接变成待办，也不默认阻止用户选定商品。
- 参数记录规格事实，待确认事项记录待办问题，笔记提供参考与依据。解决问题时可以建议更新参数，由用户确认。

## AI 的职责与能力边界

当前已实现（两处都只产出文字，用户确认后才保存）：

1. **整理草稿**：根据用户提供的文字提取一条选购草稿（名称、价格与单位、房间、分类、备注、
   明确写出的优缺点）。接口 `POST /api/record-draft`，在服务器实际运行。
2. **选购分析**（2026-10-15）：在候选详情点「让小熊分析这款」，基于这条候选已有的信息
   （名称、价格、备注、参数、优缺点、链接）产出分析，写入该候选的「选购分析」。入口在
   场景内，不跳聊天页；结果先以「分析预览（还没保存）」出现，点保存才写入并同步。
   边界：**不读取商品页面、不识别截图**，只用用户提供的内容；没有联网能力，因此不给来源
   链接（来源由用户自己维护）、不编造型号与参数，未核实的一律写「待核实」；不下「值不值得买」
   的定论。分析长文按空行分段，第一段是结论摘要。

首页清单模板、施工提示、参数字段、当前对比表和笔记关联均不是模型自动生成结果。

后续规划：
1. 房间准备：结合户型、用途、已有物品建议需要准备的东西，供用户增删。
2. 商品输入：读取可访问的商品页面或用户提供的截图/报价单，批量识别候选、规格、报价范围、来源及采集时间。网页访问和图像识别需要另行实现；取不到信息就保持未知。**这是当前最大的缺口**——它同时卡住下面的商品分析。
3. 商品分析（基础版已实现，见上）：待补的是「结合房屋条件、预算、偏好」的适配性判断，
   前提是能读到商品页面/截图。
4. 候选比较：对齐同类参数，分清单价/总价、包含范围与安装费用，说明差异以及选择理由；不在资料缺失时编造排行或性价比分数。
5. 待确认：提出关键缺口和可发给商家的问题，允许用户接受、修改、忽略。基于用户确认的回答整理结论并建议更新参数；不自动联系商家。
6. 笔记联动：建议关联已有笔记，抽取与当前房间/物品相关的注意点并链接原文；通过用户确认写入关联或待确认事项。

入口放在相应场景（整理商品、分析这款、对比差异、帮我查漏），不要求用户切到一个独立聊天页完成所有动作。默认产出简短结论、依据和下一步要确认的事，展开后才看长分析。AI 不代替用户选定、购买或确认现场安装条件。

优先实现顺序：手动待确认 → 商品页面与截图读取 → 基于真实资料的分析/对比与查漏 → 笔记推荐。先保证记录与证据可用，再增加智能建议。（「基于已有资料的分析」已提前落地，见第 2 节的选购分析。）

## 候选图片（已实现）

候选卡首图帮助快速辨认商品，多图通过缩略图切换，点击图片全屏查看。详情支持添加/删除图片关联及设置封面，最多9张；可保存商品图、尺寸图和报价截图。上传复用服务器文件接口，候选图片URL与顺序保存在当前设备，对比表同步展示首图。

已用两张独立测试图片验证真实上传、多图预览、封面调整、图片移除和刷新保留；测试候选与测试文件已清理。手机候选详情采用固定底部操作区，避免长内容遮挡按钮。

## 线下动线（已实现）

进入房间或准备项 → 拍照记录 → 上传成功生成现场候选 → 可继续拍外观/型号标签/尺寸/报价，或从相册多选 → 稍后补名称、参数和价格。已有候选也可以直接补拍，不必重新创建。手机请求后置摄像头，每次拍一张，取消和失败不会生成空候选；相册与拍照入口分开。尚未加入照片OCR或离线上传队列。

## 入口简化（用户手机实测后的调整）
移除独立拍照记录及拍照/相册双按钮，候选卡与详情统一“添加图片”。手机系统选择器已经提供拍照来源，无需应用重复提供选择。此调整覆盖上文的单独拍照入口设计。

## 候选详情简化

日常查看只显示已记录的名称、价格、照片和随手记录。参数、优缺点及次级操作收进更多信息；未知参数不在详情里铺满空行。照片默认用于查看，管理图片时再出现删除与设封面操作。底部一个编辑入口直接进入表单。已检查390px布局、折叠内容与编辑入口，类型检查及小程序构建通过。

## 海信中央空调归入全屋（2026-10-14）
用户明确要求分析京东分享商品并加入全屋中央空调。复用现有准备项和同链接候选，保存系列参考分析及官方来源；完整SKU、套餐配置、报价尚无法核实，价格保持未知。对已有设备数据进行一次性合并，保留用户填过的报价、照片、备注和选定状态；导入完成后不在后续刷新时重复添加，用户移除后也不自动恢复。界面与迁移测试已验证仅一条候选。

## 选购分析入口（2026-10-15）

上面那段海信分析当时是**写死在代码里的常量**（`data/centralAcImport.ts`），因为 App 侧没有任何产生分析的路径——它是"真结论 + 假功能"。现在候选详情有了「让小熊分析这款」：走服务端 `POST /api/analyze`，结果先作预览，用户点「保存到这条候选」才写入并同步。常量本身保留（内容真实、幂等，且已有设备的分析就在数据里），但**不再是「选购分析」的唯一来源**。保存只替换分析正文，用户维护的来源链接原样保留。
